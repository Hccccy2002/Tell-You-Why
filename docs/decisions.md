# 技术决策记录

本文件记录设计方案未明确指定、但实现 P0 所需的技术决定。任何会扩大产品范围的事项不在此自行决定。

## D-001 单页多视图而非引入路由库

- 决定：五个主要界面使用 React 状态驱动的单页多视图和轻量导航栈。
- 原因：窗口小、页面层级浅，可减少依赖和复杂度；返回与键盘操作仍保持明确。

## D-002 Rust 直接管理 SQLite

- 决定：使用 `rusqlite` 的 bundled SQLite，由 Rust 暴露窄接口命令；前端不直接访问数据库。
- 原因：依赖成熟、迁移逻辑可控，符合所有持久化和网络能力集中在 Rust 核心的要求。

## D-003 Windows 凭据方案

- 决定：通过 Rust `keyring` crate 调用 Windows Credential Manager；数据库只保存 `provider + region + model + credential_ref + key_last4`。
- 原因：不把 Key 放入前端持久化、SQLite、配置文件或日志。前端提交后立即清空输入状态，Rust 永不返回完整 Key。

## D-004 HTTP 与供应商白名单

- 决定：使用 Rust `reqwest` + rustls，Provider Registry 内置精确 HTTPS Origin；关闭自动重定向，避免携带鉴权跨域。
- 原因：调用链简单，官方端点约束容易审计。普通用户没有自定义 Base URL 输入。

## D-005 Tauri 官方插件范围

- 决定：仅使用 P0 必需的官方插件：global-shortcut、notification、autostart、dialog、opener（仅受控来源链接）。系统托盘和窗口 API 使用 Tauri 核心。
- 原因：避免给前端开放通用文件系统或 Shell；导入文件由 Rust 读取并校验。

## D-006 内容渲染

- 决定：问题、答案、解释和来源标题全部按纯文本渲染，不支持模型返回 HTML；首版不引入 Markdown 渲染器。
- 原因：P0 内容不需要富文本，可直接消除脚本、危险 HTML 和 Markdown 链接风险。

## D-007 推荐算法

- 决定：采用确定性本地加权抽取：显式兴趣优先，反馈调整主题权重，相同主题最多连续两张，最近十个指纹冷却，约 20% 在其他已选兴趣中探索。
- 原因：行为可解释、可测试，不需要长期模型记忆或向量数据库。

## D-008 演示内容与正式内容隔离

- 决定：开发版本内置一批 `demo_unreviewed` 内容，只显示“演示内容 · 未经人工复核”，绝不标记“已核验”。正式人工复核内容通过受校验的 JSON/CSV 流程导入。
- 原因：当前没有人工内容审核方，不能伪造“人工复核”状态；同时保证离线功能可开发和测试。

## D-009 提醒调度

- 决定：MVP 使用应用进程内的 Rust 定时调度器；退出应用后不调度提醒或生成。开机启动仅在用户主动开启时配置。
- 原因：避免额外 Windows 服务和计划任务，符合低打扰和低依赖目标。

## D-010 前端测试策略

- 决定：Vitest + React Testing Library 覆盖组件和关键流程；Rust 内通过 trait 替身和 Mock Transport 覆盖核心集成逻辑。
- 原因：不引入需要浏览器驱动的重量级桌面 E2E 作为 P0 构建前置条件；托盘/通知/多显示器保留人工冒烟清单。

## D-011 供应商注册表版本（2026-08-26）

- 决定：DeepSeek 使用官方 api.deepseek.com 与 deepseek-v4-flash/deepseek-v4-pro；Kimi 中国大陆使用 api.moonshot.cn，国际通道使用 api.moonshot.ai，默认模型 kimi-k3，并保留 kimi-k2.6。
- 原因：这些名称和端点已按 2026-08-26 两家官方 API 文档核对。注册表随签名应用更新，不允许普通用户覆盖。

## D-012 自动补充触发与并发

> 2026-08-27 起由 D-020 取代；保留本段作为历史实现记录。

- 决定：只有已验证且用户明确开启的供应商配置可自动补充；未读缓存降至 3 张时触发，每批最多 5 张，遵守每日上限，并用进程内原子锁保证同一时间只有一个生成任务。
- 原因：浏览“下一条”可以立即返回本地卡片，不等待模型；并发锁和限额避免重复请求与意外费用。失败只记录脱敏错误码，无效 Key 会撤销验证状态。

## D-013 Windows 通知激活

- 决定：普通通知仍使用 Tauri 官方插件；提醒通知在 Windows 上直接复用插件已经依赖的 notify-rust 后端，以区分正文点击和关闭/超时，只有正文点击才显示窗口。
- 原因：Tauri notification 2.3 的桌面封装不暴露激活事件，而产品验收明确要求“点击通知后才打开小窗”。该方案不引入新的二进制包或后台服务。

## D-014 人工内容与动态缓存隔离

- 决定：SQLite v2 为卡片增加 cache_managed 标记。模型生成卡受最近 30 张的动态缓存上限管理；内置卡和 JSON/CSV 人工导入卡不参与该淘汰。清除全部数据仍删除所有非内置内容。
- 原因：产品需要后续导入并保留 100–300 条人工复核内容，不能把面向模型成本与新鲜度的动态缓存上限误用于正式内容包。

## D-015 Windows 构建工具安装位置

- 决定：当前开发机将 Visual Studio 2022 Build Tools 主体安装到 D:\BuildTools，不在项目中硬编码该路径。Windows SDK 与部分共享组件允许 Visual Studio Installer 按微软规则保留在系统盘。
- 原因：降低系统盘占用，同时保持标准 MSVC 注册与普通 PowerShell 构建兼容，项目也不会依赖某一台机器的绝对工具路径。

## D-016 DeepSeek 结构化生成模式

- 决定：DeepSeek V4 的知识卡生成请求显式设置 thinking.type = disabled，使用 JSON Object 模式、具体结构示例和 6000 输出 Token 上限。解析器接受 {"cards":[]} 或直接数组，并兼容受控的 snake_case 字段别名。
- 原因：DeepSeek V4 默认开启高强度思考，有限输出额度可能先被推理消耗，导致最终 content 为空或 JSON 被截断。知识卡属于确定性结构化任务，不需要思考模式。格式失败后不自动发起第二次请求，避免用户一次操作产生未预期的额外费用。

## D-017 同领域单卡生成

- 决定：“再次生成同领域知识点”每次只请求并入库一张卡。后端根据当前卡片 ID 读取可信的领域信息，并在本地强制生成结果归入该领域；供应商优先选择已验证配置，最后才是仅保存 Key 的配置。
- 原因：不信任前端传入的领域标签，避免模型返回错误领域；单张生成符合按钮语义并减少费用。仅保存但未通过连接测试的配置会提示先完成连接测试，无配置时前端显示 1 秒温馨提示。

## D-018 推荐流归档与系统删除分离

- 决定：card_user_state.hidden 只表示不再进入主推荐流，SQLite v4 新增 deleted 表示从应用查询中删除。最近浏览包含 hidden 但排除 deleted；非内置卡删除时物理移除，内置卡保留 deleted 墓碑，避免启动种子重新创建。
- 原因：不感兴趣和已掌握表达的是推荐偏好，不应抹掉阅读历史；用户在最近浏览明确点击删除时才执行不可见删除。对内置卡使用最小墓碑可同时满足删除语义和幂等种子机制。

## D-019 自定义每日生成总数与用量口径

- 决定：通用设置使用数字输入允许用户把每日生成总数设为 1–1000 张，并显示“已生成数/总数”。每日边界按 Windows 本地日期计算；已生成数只累计模型任务中成功校验、去重并入库的知识点。
- 原因：自定义额度满足不同使用量，同时保留明确的费用安全边界。失败、格式错误和重复内容没有形成可用知识点，不应消耗应用内显示的成功生成数；本地日期也比 UTC 日期更符合用户对“今天”的理解。

## D-020 仅按需生成、顺序权重与小窗布局

- 决定：删除后台自动补充及“立即补充 5 张”入口，模型只在用户明确点击同领域、指定领域或随机领域生成时调用。SQLite 历史列保留兼容但始终写入关闭状态。
- 决定：随机领域候选仅包含已选择且启用的兴趣，按保存顺序分配 N、N−1…1 的权重，由 Rust 使用 SQLite 随机数完成加权抽取。拖拽排序直接更新该顺序，并提供方向键排序作为无障碍替代。
- 决定：知识小窗采用单列的元信息头部、问题主体和固定操作区；兴趣列表采用前置拖拽把手、主体说明和尾部操作的结构。布局借鉴 GitHub Primer 的聚焦式小屏布局与 ActionList 信息层级，但不新增 UI 框架依赖。
- 原因：用户能直接理解“越靠上越优先”，并避免前端操纵最终领域选择。仅按需请求降低意外费用；清晰的三段式布局在 360–420 像素宽度下更易阅读和操作。

## D-021 可展示数量口径与整行拖拽

- 决定：知识小窗顶部的“可展示”数量只统计 SQLite 中未隐藏且未删除的知识卡；浏览上一条/下一条不改变数量，不感兴趣或已狠狠涨知识后减一，成功生成后加一，历史删除后重新查询校准。
- 决定：兴趣列表使用浏览器原生整行拖放，按鼠标在目标行上半部或下半部决定插入到前方或后方；左侧把手继续提供方向键微调，不增加拖拽依赖。
- 原因：该口径与主推荐流实际可访问集合一致，避免把仅保留在最近浏览中的卡片计入；原生拖放足以满足桌面鼠标长按拖动，并保留低依赖和键盘无障碍能力。

## D-022 知识主入口与卡片二级页面

- 决定：原内容耗尽页改为始终可返回的知识主入口；有本地卡时显示“浏览现有知识点”，同时保留随机领域和指定领域生成。知识卡作为二级页面，通过小房子图标返回主入口。
- 决定：可展示数量从应用全局页头移到知识卡顶部，排列为“返回主界面、领域、可展示 N 张、生成随机领域”；不再展示预计阅读秒数。
- 原因：主入口统一承载“浏览已有”和“生成新内容”，又不破坏无 API Key 的离线核心体验。卡片顶部信息集中后更符合用户指定的信息顺序，也避免全局页头和卡片元信息重复。

## D-023 主入口批量生成与浮动提示

- 决定：主入口的生成数量同时作用于随机领域和指定领域生成，范围受“每日生成总数”约束。Rust 根据供应商每批最多 5 条的能力自动拆分请求，例如 12 条拆成 5、5、2；每批独立校验、去重和入库。
- 决定：若后续批次失败，已经成功入库的知识卡继续保留，界面按“成功数/计划数”反馈，不自动重试付费请求。
- 决定：“只剩一张卡”和“未配置模型”统一使用屏幕中央向上移动并淡出的 1 秒提示；普通错误仍使用可停留阅读的底部提示。
- 原因：用户明确选择数量后才会产生对应模型请求，同时继续受现有费用上限保护。部分成功不应因后续失败而丢失；短暂操作提示使用统一动效能减少界面占用。

## D-024 知识卡随机生成入口位置

- 决定：知识卡顶部只保留返回主界面、居中的当前领域和右侧可展示数量。随机领域生成入口移动到答案揭晓后的底部中间区，排列为“再次生成随机领域知识点、已狠狠涨知识、再次生成同领域知识点”。
- 原因：顶部仅承担导航和当前状态，生成类操作集中在答案后的行动区，信息层级更清楚；左右等宽网格保证领域名称相对卡片真正居中。

## D-025 兴趣列表鼠标指针排序与绝对位置权重

- 决定：兴趣排序不再使用 HTML 原生 draggable/DragEvent，也不通过键盘方向键换位；改为鼠标主键按住兴趣行、移动超过 4 像素后进入拖动，并依据光标命中的目标行上半部/下半部实时插入。
- 决定：排序权重由完整兴趣列表的绝对位置决定，最上方为兴趣总数，向下逐项减一。只有已选择且启用的兴趣进入随机候选，但保留其绝对位置权重。
- 原因：Windows WebView 对包含复选框和按钮的原生拖放会显示禁止落点；Pointer Events 不依赖浏览器拖放许可。绝对位置权重确保概率只由当前可见顺序决定，与兴趣勾选先后无关。

## D-026 DeepSeek 批量生成可靠性与显式续传

- 决定：DeepSeek 单批最多生成 2 张，Kimi 继续保持每批最多 5 张；例如 DeepSeek 生成 6 张会拆为 2、2、2。模型生成请求使用 90 秒总超时，连接测试继续使用 15 秒短超时，TCP 连接超时保持 8 秒。
- 决定：响应正文读取阶段继续使用同一请求超时，并把超时、空 content、finish_reason=length、外层响应异常和知识卡 JSON 异常分类为不同的脱敏错误；只记录错误码，不记录原始响应或凭据。
- 决定：后续批次失败时返回已经成功校验并入库的卡片、请求总数和脱敏警告。界面显示累计“已生成数/总数”，并在主入口提供“继续生成剩余 N 条”；只有用户再次点击才发起后续请求。
- 原因：本机真实任务记录显示 5 张批次连续两次在约 30 秒失败，而单张请求多次在约 5–7 秒成功。旧实现又把响应正文读取错误统一映射为格式错误，导致超时被误报。小批次和独立生成超时可提高稳定性，显式续传同时遵守不自动重试付费请求的费用边界。

## D-027 首选模型与跨供应商故障切换

- 决定：知识主入口提供 DeepSeek/Kimi 首选模型选择器，显示各自当前模型及“已就绪、待连接测试、未配置”状态。首选 provider_id 作为普通偏好保存在 SQLite app_settings 中，API Key 继续只保存在 Windows Credential Manager。
- 决定：生成只使用已配置并通过连接测试的供应商。首选未就绪时直接使用另一家已就绪供应商；首选在请求、解析、校验或去重阶段失败时，最多自动切换另一家一次，不再切回或循环重试。
- 决定：批量生成切换后继续处理尚未完成的数量，保留切换前成功入库的内容；两家都失败时返回合并后的脱敏原因。结果包含最终成功供应商和切换来源，界面会告知用户发生了自动切换。
- 原因：用户可以明确控制日常使用的模型，同时在供应商偶发空内容、截断、限流或网络故障时维持核心生成体验。只允许已验证配置且最多切换一次，可限制意外请求范围；但一次用户操作仍可能分别在两家供应商产生请求和费用，因此界面需明确说明自动切换策略。
