## 2. 编程语言和技术选择

**采用 Python 开发独立模块是合适的。** 本阶段使用命令行完成所有工作，后续通过进程协议由现有 Rust 核心调用。保持项目已有的 `rag-service/` 模块规划。

建议采用 Python 3.11 x64、独立虚拟环境和 `pyproject.toml` 管理依赖；具体 PaddleOCR、PaddlePaddle、PyTorch 和 Python 组合在 Windows CPU 冒烟测试后写入锁文件。本轮抽查使用了已存在的 Python 3.12 运行时，这不代表已验证完整 OCR/Embedding 依赖组合。

| 能力 | 首选技术 | 说明 |
| --- | --- | --- |
| PDF 元数据、书签和页树 | `pypdf` | 读取文档结构、页数、书签目标及页码标签 |
| 文本位置与页面渲染 | `pypdfium2` | 获取文本/字符位置，按页渲染 OCR 图像 |
| OCR 推理 | `PaddleOCR` + CPU 版 `PaddlePaddle` | 显式指定模型和本地路径，保留识别多边形及分数 |
| 版面区域检测 | PaddleOCR/PaddleX 的版面模型 | 区分正文、标题、表格及图形等区域，避免将图内散乱标注拼入正文 |
| 图像预处理 | `Pillow`，必要时 `opencv-python-headless` | 旋转、裁剪、倾斜处理及坐标变换；按需开启 |
| 结构和参数校验 | `pydantic`、`PyYAML` | 校验页、块、片段及配置协议 |
| 中文关键词索引 | `jieba` + SQLite FTS5/BM25 | 文档与查询使用相同分词、术语词典和规范化规则 |
| Embedding | `sentence-transformers` + 本地 BGE 模型 | 为检索片段生成语义向量，CPU 先跑通 |
| 向量保存与检索 | `numpy` | 保存归一化向量矩阵，初版使用精确相似度搜索 |
| 数据与任务状态 | Python 标准库 `sqlite3` | 结构化正文、引用映射、片段和任务检查点 |
| CLI 与测试 | `typer`、`pytest`，开发检查用 `ruff` | 分阶段命令、进度、恢复和质量验收 |

PDFium 提供文本页和渲染接口，具体文字顺序仍由本项目按版面整理。[pypdfium2 文档](https://pypdfium2.readthedocs.io/en/stable/python_api.html)

SQLite FTS5 提供 BM25 排序；使用前验证实际 Python SQLite 构建启用了 FTS5。中文正文先分词再入索引，不能假设默认 tokenizer 已完成中文分词。[SQLite FTS5 文档](https://www.sqlite.org/fts5.html)

对单本教材，SQLite 加 NumPy 的存储方式便于在 Windows 上部署和检查。后续语料规模或检索延迟需要时，再替换向量索引后端，保持 chunk ID 和搜索接口不变。基于归一化向量的点积可用于余弦相似度排序。[Sentence Transformers 语义检索说明](https://www.sbert.net/examples/sentence_transformer/applications/semantic-search/README.html)

## 3. 需要的模型

| 用途 | 建议候选 | 使用策略 |
| --- | --- | --- |
| 检测文字区域 | `PP-OCRv5_server_det` | 在需要重新识别的页面上运行；CPU 速度不足时对照评估 mobile 检测模型 |
| 识别中英文文字 | `PP-OCRv5_server_rec` | 以正文质量为优先的初始候选，实际效果由这本教材的人工样本判定 |
| 区分版面区域 | `PP-DocLayout-S` | 先评估轻量版面模型；图表/公式边界识别不足时调整模型或标为待处理 |
| 语义向量 | `BAAI/bge-small-zh-v1.5` | 为合格片段建立中文语义索引；固定模型 revision、分词器和编码配置 |
| 页面方向 | `PP-LCNet_x1_0_doc_ori`，可选 | 只在方向检测确有需求时启用 |
| 复杂表格/公式 | `PP-StructureV3` 的对应模块，可选增强 | PP-StructureV3 是多个模型组成的流程；按模块验证和启用，不默认加载整套模型 |

PaddleOCR 官方文档仍列出 PP-OCRv5 的检测/识别模型并支持显式选择。这里把 v5 作为可复现基线候选，不依赖库当前默认模型；下载前确定版本、来源和校验值。[PaddleOCR 模型与调用文档](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/OCR.html)

版面模型及可选的表格、公式模块见 [PP-StructureV3 文档](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/PP-StructureV3.html)。这一类教材的公式内容必须单独检查，普通 OCR 文本分数不能证明公式正确。

BGE 小模型的配置为 512 维表示、512 个位置长度；正文加标题和特殊 Token 的实际输入不得超上限。文档侧不添加查询指令，查询侧按模型卡配置。[BGE 模型卡](https://huggingface.co/BAAI/bge-small-zh-v1.5)、[模型配置](https://huggingface.co/BAAI/bge-small-zh-v1.5/raw/main/config.json)

本阶段所需模型均为本地推理模型，无需调用 DeepSeek/Kimi 生成内容。首次准备模型需要下载，之后显式使用本地路径。OCR、版面与 Embedding 按阶段加载，尽量避免所有模型同时占用内存。

## 5. 各阶段的处理规则与产物

### 步骤 1：接收文件并建立任务

计算原文件 SHA-256，校验实际格式、页数和磁盘空间，保存一份原件副本。建立文档登记和持久任务，记录输入页范围、处理配置、模型版本和程序版本。同一文件和配置再次运行时复用已有阶段结果。

产物：文档清单、原件副本、书签原始记录、页级任务状态。

### 步骤 2：先验证代表性页，再决定全书 OCR 策略

用约 20 页覆盖正文、标题、双栏目录、表格、公式、图形及低质量页。首批包含已抽查的 3、9、50、300 页，其他样本从各章补充。

对照旧文本与新 OCR，人工检查正文、数字、上下标和否定词。原文本层可能有错但不含乱码，不能只用字符数/乱码率决定是否复用。对本书采用保守路由：未通过样本质量验证的同类页面进入重新 OCR 或人工检查。

若新 OCR 也达不到要求，相关区域保存为待检查资料，并从可供生成的证据集合中排除。原文本层和新 OCR 都保留，选择结果记录依据，不能自动拼接成两份重复正文。

产物：模型/参数选择报告、页型路由规则、质量门槛和样本校对记录。OCR 尚未实测，具体重识别页数待本步骤确定。

### 步骤 3：逐页提取、识别和恢复版面

初始渲染参数以约 300 DPI 试验，结合扫描源分辨率、OCR 缩放上限和耗时调整。按页加载、处理后释放；图片不一次性全部驻留内存。

使用版面区域分离正文、标题、页眉页脚、表格、图和公式；识别结果保存块类型、多边形、阅读顺序和质量信号。采用统一的显示方向、页左上角为原点的坐标约定，记录旋转/裁剪/缩放变换，可反向定位至原 PDF。

默认保留公式及图形原图区域；只有结构可靠的表格才能进入文本证据，拆分时重复表头。复杂区域的图中文字不能作为连续正文索引，待补充理解的限制随片段保留。

产物：逐页原始提取 JSON、OCR 候选、结构化正文块和待检查区域。

### 步骤 4：整理章节和清理正文

优先解析 72 个书签，校验目标页和章节顺序。无有效页码的“篇”节点作为分组保留，依据相邻章范围推断位置并标记；书签未覆盖的小节通过编号、版面和目录补充，允许配置文件人工修正。

去除重复页眉页脚、恢复断行和跨页段落，同时保存原始块到规范化文本的映射。字符规范化不能破坏二进制数、单位、负号、上下标等语义；尤其不能把指数简单转换为相邻普通数字。

封面、出版信息、目录、正文、习题、参考资料等分别标记。默认正文参与学习证据检索；目录用于导航，习题单独筛选，图表/公式限制明确展示。

产物：`chapters.json`、`blocks.jsonl`、页码对应表、清理与排除报告。

### 步骤 5：分块并建立来源映射

以章/节、段落、列表和表格为边界。BGE 初始正文目标 320 Token、必要重叠约 40 Token；实际连同章节标题和特殊 Token 必须不超过 512。边界和大小在样本检索中调整，不按固定页数或字符数机械切分。

每个 chunk 至少包含知识库 ID、文档哈希、提取版本、分块版本、章节路径、正文、来源块/字符范围、页码/坐标、质量及内容限制。跨页块保存多个位置范围。

稳定 chunk ID 由资料身份、提取版本、规则版本和源范围共同确定。元数据或学习摘要与原文分开存储；此阶段不让生成模型改写教材。

产物：`chunks.jsonl`、Token 统计、源位置映射及分块抽查报告。

### 步骤 6：建立关键词和语义索引

中文正文和查询均先用 jieba 及固定术语词典处理，再使用 SQLite FTS5/BM25。保留原文列，分词列用于索引；术语大小写和连字符采用一致规则。

使用本地 BGE 模型分批编码合格片段，保存 L2 归一化的 float32 向量；向量矩阵第几行对应哪个 chunk，在同版本 SQLite 的 `vector_rows` 表中明确记录。实际批量大小从 CPU 基线调整。

验证向量行数等于参与语义索引的片段数、维度正确、无 NaN/Inf，文本索引和向量索引对应同一资料/配置版本。查询先限定知识库、版本、章节和质量状态，融合前按 chunk 去重。

产物：包含 FTS5 的 `knowledge.sqlite`、`embeddings.npy` 和模型/编码配置。

### 步骤 7：校验后发布知识库

在临时版本目录完成所有写入，关闭数据库、完成必要的 WAL checkpoint，再核对数据库完整性、文件哈希、片段/向量一致性及来源可读性。确认后发布不可变版本并原子更新 `active.json`。

`manifest.json` 记录资料哈希、处理版本、模型 revision、分词/分块配置、文件校验值、页面状态、可用内容覆盖率和受限区域。部分失败可发布明确的 `partial_ready`，但不得显示为全部识别成功。

最终引用需要的块、原文及图片进入持久版本目录，不能继续依赖可以被清理的 `work/`。相同原 PDF 重新 OCR 会产生新的提取版本，旧来源定位保持可读。

产物：可独立加载的知识库版本、活动指针和验收报告。

## 6. 本地数据库的最小结构

| 表 | 主要内容 |
| --- | --- |
| `documents` | 文档身份、原文件哈希、原件位置、题名、页数、提取版本 |
| `pages` | PDF 页序号、书内页码、提取方式、质量、状态和限制 |
| `blocks` | 原始/规范化文本、类型、坐标、阅读顺序和转换映射 |
| `chapters` | 章节层级、起止范围、来源依据、推断/修正状态 |
| `chunks` | 片段正文、章节、源范围、Token 数、质量与版本 |
| `chunk_locations` | 一对多的 PDF 页及区域映射，支持跨页来源 |
| `chunks_fts` | 已分词的检索列及稳定行身份 |
| `vector_rows` | 向量行号到 chunk ID 的对应关系 |
| `assets` | 图表、公式等长期原页区域及限制 |
| `index_metadata` | 同版本的解析、分块、分词及 Embedding 配置 |

工作区的 `job.sqlite` 单独记录任务和页/阶段检查点，最终发布库用于只读查询。后续卡片、收藏和学习状态继续由 APP 的业务 SQLite 管理。

## 7. 计划中的使用命令

以下为拟开发 CLI 的调用示例，尚不能运行；参数语义在实现时保持一致。安装和模型下载也将在开发阶段执行。

```powershell
# 在 Python 工程目录建立并验证环境后执行
tellwhy-kb inspect --pdf "D:\Tell-You-Why\计算机组成原理.pdf"

# 首轮只做代表页试验，输出旧文本与 OCR 对照产物
tellwhy-kb ingest --pdf "D:\Tell-You-Why\计算机组成原理.pdf" --kb computer-organization --pages "3,9,50,300" --until structure --config configs/ingest.yaml

# 规则通过样本验证后，执行完整资料准备并发布
tellwhy-kb ingest --pdf "D:\Tell-You-Why\计算机组成原理.pdf" --kb computer-organization --config configs/ingest.yaml

# 中断后按已有任务身份恢复
tellwhy-kb resume --job <job_id>

# 检查知识库结构、来源映射及索引一致性

```

首轮四页仅验证处理链路，不能据此确定全书质量；正式路线选择至少扩充至约 20 页的分组样本。全书任务复用配置一致、已经成功的页结果；不在首轮样本运行时发布为“全书知识库”。

## 8. 开发步骤与验收

| 开发步骤 | 工作及交付物 | 粗估开发日 |
| --- | --- | --- |
| 1 | 工程、环境及模型管理；CPU 冒烟验证；明确文件和数据协议 | 1 |
| 2 | 文件检查、书签、原文本层与位置、单页渲染 | 1 |
| 3 | OCR/版面适配器和质量路由；约 20 页样本对照 | 2–3 |
| 4 | 章节、正文整理、公式/图表限制与源映射 | 1–2 |
| 5 | Token 分块、来源位置和分块检查 | 1 |
| 6 | FTS5、Embedding、向量一致性和搜索 CLI | 1–2 |
| 7 | 436 页全量试运行、恢复/重复运行、发布和验收报告 | 1–2 |

本阶段粗估 **8–12 个开发日**，覆盖 Python CLI 与这本教材的资料准备，不含桌面 UI、生成模型接入和完整桌面安装包交付。工期在 OCR 样本质量和 CPU 耗时测定后调整，实际全书处理耗时单独记录。

完成条件：

- 436 页全部有成功、空白/非正文排除、待检查或失败状态，报告数量可对账。
- 10 个章级书签起点与 PDF 核对；无目标书签不丢失也不错误映射到第一页。
- 抽取样本能回到原页对照；普通正文 CER 以 ≤ 5% 为初始目标，数字/单位/上下标另评。缺乏可靠解析的公式、图表明确保留限制。
- 每个可检索 chunk 有可访问的原文范围；全量输入无静默截断，源版本信息完整。
- 文本/向量索引同版本，向量行、维度及 chunk 映射全部一致；重新加载后可正确查询。
- 建立约 30 条带人工证据标注的检索问题，覆盖术语、改写、跨段条件和资料不足；开发/保留集分开。可回答任务 Hit@5 ≥ 90% 为初始目标，报告实际分子/分母及覆盖情况。
- 重复运行不新增重复文档/片段；中断恢复仅补做未完成或失效阶段。重跑配置变更时生成新版本。
- 程序重启及模型资源已准备后的离线运行能够加载知识库，输出原文、章节、PDF 页码及限制。

最终交付：Python 工程、锁定配置及模型清单、本案例的知识库版本、章节和覆盖率报告、OCR 对照报告、检索质量报告，以及从零构建和恢复任务的操作说明。
