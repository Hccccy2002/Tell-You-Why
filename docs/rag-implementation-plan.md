# Tell You Why：计算机硬件 RAG 执行计划

计划日期：2026-09-09。状态：**计划已制定，RAG 尚未实现**。资料收集、来源记录和提取完整性检查已完成。本文件中的模型、索引、接口、指标与工期均为建议方案或待验收目标。

本方案已纳入 [PDF、知识库、RAG 与随机学习完整开发路线](end-to-end-development-plan.md)。统一路线规定当前开发顺序及 sidecar 进程管道接入方式，取代本文早期的 FastAPI 桌面接入建议；本文保留现有教材语料和 RAG 评测的专题细节，工期不重复累加。

## 1. 第一版目标

用户选择“计算机硬件基础”，应用从已收集资料中检索证据，生成带段落引用的知识卡；点击引用可以查看当时使用的原文。围绕卡片追问时重新检索。资料不足、过时或需要未收录图表时，明确说明限制。

第一版采用固定的“检索 → 证据检查 → 生成 → 引用校验”流程。后续在基础评测稳定后，再增加 Agent 自主改写查询与补充检索。

现有语料：35 篇、2 部教材、78,700 个正文字符，入门 21 篇、进阶 14 篇。25 篇含未收录图表或排版块。来源完整性已经核对，全文尚未逐条事实核验。

历史语料的唯一正文入口为 `data/rag/computer-hardware/corpus.jsonl`。该旧资料包已从当前源码分发中移出；本文仅记录早期方案，当前应用通过用户自行导入的 PDF 建立知识库，见 [PDF 使用指南](pdf-desktop-guide.md)。重新准备类似语料时，应记录作者、来源和许可，并避免把原文镜像、节选及元数据一并递归索引造成重复。

## 2. 总体流程

离线准备，在资料或索引配置变化时执行：

```text
核验语料与版本
→ 解析正文、章节及来源位置
→ 按结构分块，保留适用条件和定位信息
→ 中文分词与关键词索引
→ Embedding 与向量索引
→ 检索评测
→ 发布一个可追溯的索引版本
```

每次生成或追问时执行：

```text
理解任务与领域
→ 生成检索请求
→ 关键词/向量检索，融合去重
→ 选择证据并检查覆盖范围
→ 资料不足则停止或给出部分结果
→ 模型基于证据生成带引用的结构化结果
→ 校验结构、引用身份和结论支持关系
→ 保存知识卡、证据快照和执行记录
→ 展示答案与可展开原文
```

检索分数不是事实置信度。成功运行检索也不等于资料足以支持生成。

## 3. 建议架构

针对求职项目，建议新增独立的 Python 检索模块；先提供 CLI，在桌面集成阶段再提供 FastAPI 本地接口。现有 Rust 核心继续负责模型请求、系统凭据、知识卡保存和业务流程。

| 模块             | 责任                                                   |
| ---------------- | ------------------------------------------------------ |
| React/Tauri 前端 | 领域选择、生成进度、知识卡、引用原文面板               |
| Rust 业务核心    | 调度检索、调用 DeepSeek/Kimi、校验与保存结果、控制预算 |
| Python 检索模块  | 资料解析、分块、中文分词、Embedding、搜索和证据读取    |
| 独立知识库文件   | 原文版本、片段、索引配置及向量；由检索模块单独管理     |
| 现有业务 SQLite  | 知识卡、用户记录、卡片与证据关联、任务摘要             |

默认检索技术：中文分词后的 BM25 基线；本地中文 Embedding 候选 `BAAI/bge-small-zh-v1.5`；小规模语料使用 NumPy 精确向量搜索，结合按排名融合的 RRF。语料规模扩大后，根据实测迁移索引实现。重排序器作为独立对照实验，不进入第一条可运行路径的必需依赖。

BGE 候选为 512 维中文模型。实施时锁定模型 revision、分词器与依赖版本，按官方模型卡配置 query instruction、池化与归一化，并测量本机 CPU 延迟和内存。模型许可与教材许可分别记录；模型许可不能改变语料许可。[BGE 模型卡](https://huggingface.co/BAAI/bge-small-zh-v1.5)

本地检索服务仅监听回环地址，Rust 管理其生命周期和会话凭据。该服务不接收供应商 API Key；外部 LLM 请求继续走现有供应商白名单。对本地服务增加专用的固定目标访问通道，不能因此放开现有 HTTP 客户端的任意 URL 访问。

部署顺序：CLI 实验 → 桌面开发模式集成 → 打包本地服务与模型并验收。最后一项单独估工，不能将“开发环境能运行”视为“安装包已交付”。

## 4. 分阶段工作与验收

### 阶段 0：冻结资料和评测定义（约 1 个开发日）

- [ ] 运行现有语料完整性检查，记录语料 manifest 的哈希。
- [ ] 按主题、难度与适用条件筛选，明确不支持当前型号选购、实时价格和图表细节。
- [ ] 准备 50 个任务：30 个基础问题、10 个多证据或受数量/难度约束的生成任务、5 个资料不足/过时/依赖图表任务、5 个异常或对抗任务。
- [ ] 人工标注可接受知识点、证据原文范围、必需适用条件和资料不足时的期望行为；这些标注单独存放，不能进入知识索引。
- [ ] 先固定任务分组与开发/测试划分，建议 30 个开发任务、20 个保留测试任务；同概念改写、邻近证据和同原文文件产生的近似任务放在同组，优先分组隔离。实际比例随分组大小调整并记录。

交付物：语料版本清单、评测任务草案、人工核对记录和开发/测试划分。任务与证据按原始章节分组；所有源资料仍可以存在检索库中，这是开放资料检索评测，不是把答案标注放进 Prompt。

验收：每个可回答任务有人工检查过的原文证据；没有把“当前最新显卡/接口价格”标成这批旧资料能够回答的问题。

### 阶段 1：正文分块和来源定位（约 1–2 个开发日）

- [ ] 只读取 corpus 中的 text，章节标题与 topic 用于检索上下文，limitations 单独保存。
- [ ] 优先按标题、段落、列表、代码块和表格边界切分；超长段落再按句子拆分。
- [ ] 初始目标正文 256–384 个 Embedding Token，必要时重叠 32–64 Token；实际输入连同标题和特殊 Token 必须不超过模型上限，不允许静默截断。
- [ ] 表格按行分组时重复表头并保留前后的适用条件；图表占位不作为证据或主要检索内容。
- [ ] 对每个片段保存 doc_id、chunk_id、来源版本、正文字符/行范围、原文行范围、主题、难度、许可、限制及哈希。
- [ ] chunk_id 由文档身份、版本、分块规则版本和定位范围确定；标题用于搜索，但不得伪装成正文原句。

交付物：chunks.jsonl、来源映射、分块统计及 10 个典型片段抽查记录。

验收：所有片段均能回到原文；没有丢失否定词、范围限制或表头；重跑结果稳定且不重复；不存在超出模型长度后被截断的片段。

### 阶段 2：先验证检索，再调生成（约 2 个开发日）

- [ ] 实现中文分词 BM25 基线，保留 CPU、DDR、PCIe 等技术术语与英文缩写。
- [ ] 生成本地向量，文档和查询使用同一模型/分词器版本以及匹配的编码配置。
- [ ] 实现关键词检索、向量检索、混合检索三种可切换模式。
- [ ] 初始每路取 Top 20，按 RRF 融合、去重，选择约 4–6 个片段进入上下文；根据开发集调整数量。
- [ ] 抽查检索结果，区分术语没匹配、分块失去条件、相关但不能回答、重复片段占满上下文等失败类型。
- [ ] 设置上下文预算；证据来自同一章节时合并重叠片段，需要时补充相邻段落。

交付物：检索 CLI、版本化索引和检索报告。报告记录 Recall@K、Hit@K、MRR、延迟及失败样例。

验收建议：可回答任务的 Hit@5 目标为至少 90%；这是起始目标，不是当前成绩。Hit@5 指前 5 条至少命中一份有效证据；多证据任务另算必要证据覆盖率。按分组后的实际样本数同时报告分子/分母。

知识范围过滤和证据充分性判断独立于排名阈值。相似度不作为百分比置信度呈现。

### 阶段 3：带证据生成知识卡（约 2 个开发日）

按领域生成：

1. 使用领域与难度检索多个候选知识点。
2. 与已有知识卡、已掌握主题比较，选择有证据且尚未重复的知识点。
3. 为各知识点组织独立证据包，生成问题、简短答案、解释和逐项引用。

围绕卡片追问：

1. 根据当前卡片和近期对话解析“它、这个”等指代。
2. 用明确的问题重新检索，区分本次证据与历史 AI 回复。
3. 在资料范围内回答，并给出本次回答的引用。

两种模式共享检索和校验组件。历史 AI 内容只帮助理解对话，不自动成为事实证据。

- [ ] 扩展模型请求结构，加入由程序提供的 evidence_id、原文、适用范围和任务约束。
- [ ] 模型只返回引用 ID，作者、来源 URL、版本和原文位置由程序解析填充。
- [ ] 对简短答案、详细解释和“为什么值得知道”中的事实性主张建立证据关联。
- [ ] 支持 completed / partial / insufficient_evidence 等任务结果。
- [ ] 资料只支持 3 张时，即使用户请求 5 张，也返回 3 张及不足原因；调整现有必须返回固定数量、最小解释长度的生成策略。
- [ ] 检索故障与资料不足分别显示；有依据模式不能静默退回无证据生成。

交付物：RAG 生成接口、Prompt 版本、结构化结果与任务状态定义，至少一个实际模型端到端样例。

验收：同一请求返回的每个引用都属于该请求的证据集合；故意伪造引用会被程序拒绝；不编造 URL；旧参数不能被解释为当前规格。

### 阶段 4：引用校验、存储和桌面展示（约 2–3 个开发日）

- [ ] 程序核对引用 ID、证据版本、范围、原文快照和结果结构。
- [ ] 用人工样本校准结论支持关系判断；模型评审只作为辅助，区分支持、部分支持、不支持和冲突。
- [ ] 结构有效且有证据的卡片标为 source_grounded；verified 继续要求实际的人工核验流程。
- [ ] 扩展 Rust/TypeScript 的来源模型，兼容旧卡片，新增片段及引用关系存储。
- [ ] 知识卡与其证据快照或可长期保留的版本引用一起事务保存。
- [ ] 添加引用原文面板，展示段落、章节、版本、来源和限制，支持打开原始来源。
- [ ] 检查删除资料、清空数据和模型运行的并发边界；删除索引不能无提示破坏现存知识卡的引用。
- [ ] 索引更新采用新版本构建后切换；缓存键包括正文哈希、模型版本和配置版本。

交付物：数据库迁移、兼容旧卡片的接口、来源面板、删除与更新规则。

验收：点击引用能看到实际证据；应用重启后仍可查看；重新建立索引不会让旧引用错误指向新段落；离线阅读已有知识卡继续可用。

### 阶段 5：回归评测和求职展示（约 1–2 个开发日）

- [ ] 在固定模型和任务设置下比较直接生成、关键词 RAG、向量 RAG、混合检索 RAG。
- [ ] 先在开发任务调参，再运行保留测试任务；公布语料、Prompt、模型、分块与索引版本。
- [ ] 可回答任务至少重复运行 3 次，报告平均结果与失败情况；Mock 用于确定性异常测试，真实模型用于质量评测，两者分开报告。
- [ ] 记录引用支持率、证据覆盖率、答案正确性、资料不足处理率、任务完成率、P50/P95 延迟和 Token/费用。
- [ ] 将供应商内部重试与跨供应商切换统一计入单任务调用次数、耗时和费用预算；日志不保存 Key。
- [ ] 形成评测报告、失败案例分析、架构图和 3 分钟演示。

建议初始验收目标：入库引用身份/位置有效性 100%；人工抽查的引用支持率和关键结论证据覆盖率各至少 90%；不足资料任务正确处理率至少 90%。质量目标均需结合实际样本数公布，不宣称代表全领域正确率。模型评分必须经过人工抽查。

性能先在实际机器测量冷启动和热运行基线，再设定目标；不要预先承诺毫秒级检索或固定生成耗时。能检索到有关内容，不代表能回答全部问题；只生成很少内容也不能通过覆盖率和任务完成率验收。

## 5. 现有项目的改动位置

| 位置                                  | 计划改动                                               |
| ------------------------------------- | ------------------------------------------------------ |
| 新增 rag-service/                     | 离线导入、分块、Embedding、检索、证据读取、CLI/FastAPI |
| src-tauri/src/providers/mod.rs        | 为生成与追问请求携带证据；返回带引用的草稿结果         |
| src-tauri/src/commands.rs             | 加入检索和证据校验，支持部分完成、预算和执行记录       |
| src-tauri/src/models.rs、src/types.ts | 来源、证据引用、任务状态和索引版本结构                 |
| src-tauri/src/db.rs                   | 版本化迁移、引用关联、证据快照、与数据清理的衔接       |
| src-tauri/src/content.rs              | 扩展结构/引用校验；不将其误称为自动事实核验            |
| src/components/KnowledgeCardView.tsx  | 展示逐项引用及原文面板                                 |
| src/lib/api.ts                        | 桌面命令封装及演示模式兼容                             |

所有新模块与接口名均为规划，尚未创建或实施。现有业务 SQLite 仍由 Rust 管理；检索服务不直接写用户收藏、追问等业务数据。

## 6. 工期与交付边界

熟悉当前代码的一名开发者，完成开发模式下的可演示版本，粗估 **10–15 个开发日**，含真实模型评测和人工证据检查。Windows 本地服务、模型随包分发和安装/升级验收另估 **2–4 个开发日**，待模型体积、运行时和打包方式验证后调整。

第一批可执行工作是阶段 0 和阶段 1：评测定义、分块和引用定位。它们可离线完成，Embeddings 安装/推理和真实模型费用从后续阶段开始。

基础 RAG 达标后，下一版 Agent 增加按证据缺口改写查询、读取相邻段落、补充检索以及有上限的修正。用相同任务集比较增加的成功率、耗时和费用；不因加入循环就自动认定更优。
